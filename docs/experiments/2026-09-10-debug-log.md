## 0. 起点

上一轮的交付状态是「构建通过、冒烟实例上端到端证明最优」。但它是**假绿**：跑通的只有
`standard_weighted.wcnf` 这种 2 变量的小例子，而混合协议的核心——CASH 停下来把控制权交给
SPB——在真实 MSE 实例上**一次都没有执行过**。下面三个独立缺陷叠加在一起，任何一个都足以
让混合退化成纯 CASH。

## 1. 缺陷一：SCIP 首调用吞掉整个预算

### 现象

```
$ ./build/HybridMaxSAT/hybridmaxsat --config Hybrid --budget 40 --cash-window 2 \
      --instance-id hs7 .../MSE23W/hs-timetabling_wt-BrazilInstance7.xml.wcnf /tmp/hw/hybrid.jsonl
{"event":"run_complete",...,"final_lb":"0","final_ub":"4621","spb_certificate_ub":null,
 "cash_deadline_polls":0,"exit_reason":"budget"}
rounds=0
real 0m43.060s
```

窗口设成 2 秒都没有一轮 SPB，`cash_deadline_polls` 为 **0**——CaDiCaL 一次都没问过终结器。
这说明 43 秒里根本没有发生 SAT 调用。

### 定位

`MsSolver.cc` 在进入自己的 CDCL 循环之前先做：

```cpp
if (opt_use_scip_slvr && weight_sum < ... && l_True ==
    scip_solve(&assump_ps, &assump_Cs, &delayed_assump, weighted_instance, ...))
    return;   // 走到这里说明 SCIP 解掉了；否则继续到下面的 while(1)
```

而 `ScipSolver.cc` 里这个调用**同步**执行，且只在 `opt_scip_cpu > 0` 时才设时限：

```cpp
if (opt_scip_cpu > 0) SCIPsetRealParam(scip, "limits/time", opt_scip_cpu);
```

`opt_scip_cpu` 默认 0 = 无时限。hs-timetabling 有 55532 变量 / 207621 子句，通过了
`scip_solve` 开头的规模闸门（要求 < 100000 自由变量、< 600000 子句、< 100000 软子句），
于是 SCIP 连预处理都跑不完就把 600 秒全吃了。用原始二进制复核：

```
$ ./build/CASHWMaxSAT-DisjCad-S6/code/uwrmaxsat/uwrmaxsat -v2 -cpu-lim=40 -nm <hs7>
c Starting SCIP solver in a separate thread (with time-limit = 0s) ...
Presolving Time: 18.46
c Wall clock time        : 21 s
s UNKNOWN
```

注意这是**未修改的 CASH**：在这类实例上它本来就把预算花在 SCIP 上，与我们的改动无关。

### 修复

`hybrid_main.cpp` 新增 `apply_scip_limit()`：`CASH` 与 `Hybrid` 都把 `opt_scip_cpu` 设为
CASH 窗口长度（默认 15 秒）。`Hybrid` 的理由是窗口必须能收得住；`CASH` 的理由是**可比性**：
它必须与 `Hybrid` 的 CASH 分量一样，否则两者差的就不是 SPB 而是 SCIP 时限。

修复后同一实例立刻出现轮次：

```
{"event":"spb_round","round":1,"cash_seconds_before_spb":10.0004,...,"spb_ub":-1,...}
{"event":"spb_round","round":2,"cash_seconds_before_spb":23.0011,...}
{"event":"spb_round","round":3,"cash_seconds_before_spb":36.0018,...}
cash_deadline_polls: 786325
```

轮次间隔 13 秒 = 10s CASH 窗口 + 3s SPB 窗口，与协议完全一致；终结器被询问 78 万次。

## 2. 缺陷二：传给 SPB 的赋值长度不对（导致每次交接都抛异常）

上一步之后，一旦窗口到点**真的去调用 SPB**，运行立刻失败：

```
$ ./build/HybridMaxSAT/hybridmaxsat --config Hybrid --budget 40 --cash-window 10 \
      --spb-window 3 --scip-cpu 10 <hs7> /tmp/hw/h4.jsonl
SCIP timeout with lower and upper bounds: [-9223372036854775524, 9223372036854775807]
$ echo $?
1
$ cat /tmp/hw/h4.err
hybridmaxsat error: initial solution must contain num_vars + 1 entries
```

### 定位

`MsSolver.cc` 按 **CASH 自己的**变量数造向量：

```cpp
std::vector<int> partial_assignment(pb_n_vars + 1, -1);
```

`pb_n_vars` 包含 CASH 转换目标函数时新增的松弛变量与 sorter 变量；而 SPB 是**独立解析原始
WCNF** 的，`LocalSearchSolver::validate_initial_solution()` 要求长度恰好是原始变量数 +1：

```cpp
const std::size_t expected = static_cast<std::size_t>(backend_.originInstance.num_vars) + 1;
if (initial_solution.size() != expected)
    throw std::invalid_argument("initial solution must contain num_vars + 1 entries");
```

两者只在「实例没有引入任何新变量」时才相等，而 `standard_weighted.wcnf` 恰好是这种情况，
所以小实例冒烟掩盖了这个缺陷。**在此之前，混合协议在任何真实实例上都不可能成功交接。**

### 修复

- `SPBMAXSAT2/src/Solver/local_search_solver.h` 新增 `num_vars()`，暴露原始 WCNF 变量数。
- `HybridCoordinator::find_upper_bound` 把 CASH 的向量**截断**到 `num_vars() + 1` 再交给 SPB
  （两者都按 WCNF 顺序 1-based 编号、元素 0 不用，因此前缀就是共享部分），并在长度不足时
  抛出可读错误而不是让 SPB 去报一个看不懂的消息。

修复后同一实例得到 3 轮完整交接，`propagated_original_variables: 2634`（即 CASH 持久传播
状态覆盖的原始变量数）。

## 3. 缺陷三（早先已修）：预算机制无效

- `-cpu-lim` 把 `RLIMIT_CPU` 设在预算 **1/4** 处、靠一次性 `first_time` 标志吸收第一次
  `SIGXCPU`；实测在大实例上不被吸收，CASH 在约 1/4 预算处就停了。→ 全部改墙钟预算。
- CaDiCaL 的 `SimpSolver::limitTime()` 装的 alarm 实测无法打断一次长调用。
- `CaDiCaL::Signal::set()` 会把 SIGTERM 处理器换成 `catch_signal`，其 else 分支直接
  `::raise(sig)`，信号处理器里写记录的做法会当场死掉；且处理器里用 `tolong(Int)` 会
  `xstrdup` 并可能抛 `Exception_IntOverflow`，本身就不是异步信号安全的。

现在的三层结构：**CaDiCaL 终结器**（正常路径，窗口边界返回，界值完好）→ **看门狗线程**
（预算+3 秒，绕过信号，try/catch 里读界值）→ **调度脚本的 `timeout`**（预算+15 秒 SIGTERM，
+30 秒 SIGKILL）。每层都可能独立写记录，用一次 `std::atomic::exchange` 保证「一次运行只有
一条记录」。

## 5. 记录格式的两处修正

1. **`+oo` → `n/a`。** `Int_MAX`（CASH 的「无穷」）被 `toString()` 渲染成 `+oo`，但作为
   **下界** `+oo` 语义是反的；而 SPB 根本不推导下界，写 `+oo` 更是不实。改为 `n/a` =
   「该配置不产生这个值」。
2. **SPB 的 incumbent 补全。** SPB 模式此前 `final_ub` 有值而 `final_incumbent` 是 `n/a`，
   自相矛盾；现在 `final_incumbent` 取自证书。混合模式下若 CASH 结束时手里没有模型（窗口
   边界打断了它的 SAT 调用），而 SPB 有，则用证书回填 `final_ub` / `final_incumbent`，
   但**不动** `cash_proved_optimal`——只有 CASH 的精确推理能宣布最优。

调度脚本相应新增：`with_ub`、`productive_rounds` 两列，以及 `summary.md` 末尾两行
「零轮次的混合运行数」「有轮次但 SPB 从未给出可行解的运行数」。最后一类尤其重要：它把
「交接根本没发生」与「交接发生了但 SPB 没贡献」区分开，否则两者在轮次数上无法分辨。

## 6. 已知限制（供选窗口/选实例时参考）

- **SPB 在超大实例上给不出可行解。** hs7（55532 变量）上独立 SPB 跑满 40 秒
  `spb_certificate_ub: null`；把混合的 SPB 窗口放宽到 20 秒同样 `spb_ub: -1`。这不是协调器
  的问题，是 SPB 自身在带硬子句的大实例上的能力边界。这类实例上混合轮次必然「有轮次、
  无贡献」。
- **CASH 的持久传播状态覆盖比例很低。** hs7 上每轮约 2634 / 55532 个变量有值，其余由 SPB
  自行补全。这既是 `Hybrid` 与 `Hybrid-NoInference` 的差异所在，也是短窗口内在超大实例上
  难有可行解的原因。
- **窗口起点在 SCIP 之后。** `instance_start_wall_` 在 CASH 首次到达调度点时置位，而同步的
  SCIP 调用在那之前，所以「第一个 15 秒窗口」实际包含了一段 SCIP 时间。这一点在
  `cash_seconds_before_spb` 的数值上看得出来（第 1 轮通常在窗口长度处），复盘时须知。

## 8. 缺陷四：SCIP 证出最优时从异步线程 `_Exit(30)`，整条记录丢失

### 现象

Stage 1 跑到 89/600 时出现 18 次 `FAIL`，全是 `exit 30`、`no run_complete record`，且
命中三组实例 × 三个 CASH 系配置（SPB 不受影响）：

```
$ grep FAIL runs/debug50/experiment.log | cut -f5 | sort | uniq -c
      8 MSE23W/frb_wt-frb25-13-1.wcnf
      9 MSE23W/Security-CriticalCyber-PhysicalComponents_wt-test54--n-15000.wcnf
      9 MSE23W/Security-CriticalCyber-PhysicalComponents_wt-test75--n-20000.wcnf
```

每个失败都在约 5 秒（或 45~174 秒）处，stderr 空、stdout 停在 SCIP 的统计块。

### 定位

`ScipSolver.cc:298`：CASH 的 SCIP 组件证出最优后，在**非 ipamir** 路径里 `outputResult()`
然后 `std::_Exit(30)`。`_Exit` 不跑析构、不触发 atexit、主线程再拿不回控制权，所以
`main()` 末尾的 `write_run_complete()` 根本没执行——记录丢失。这正是 CASH 独立 CLI 的
「解完就退出」约定，泄漏进了我们的嵌入运行器。它偏偏命中「CASH 证明最优」——本实验的
主指标——的那些实例。同文件 `:160` 还有一处 UNSAT 路径的 `std::_Exit(20)`，同一性质。

### 修复

- `Main_utils.cc` 新增 `opt_embedded_runner` 标志，`hybrid_main.cpp` 在 `apply_maxsat_options()`
  里置位。
- `ScipSolver.cc` 两处 `_Exit` 改为：嵌入模式下 `goto clean_and_return`（最优路径同时置
  `opt_scip_proved_optimal` 原子标志），独立 CLI 保持原 `_Exit` 不变。
- 运行器新增 `scip_proved_optimal` 字段与 `exit_reason=optimum_scip`，把「ILP 分量证明最优」
  和「CDCL 证明最优」分开；`fill_from_solver()` 对 SCIP 证明补全 `final_lb = final_ub =
  incumbent`（SCIP 证出的最优两侧都已知，不再留一个与最优并存的空下界）。
- 协调器与 CASH-only 回调的 `should_stop()` 在 SCIP 已证出最优时立即结束实例（§4 的
  「CASH 一旦证明最优立即结束」对 ILP 路径同样成立）。

验证（同一 test54 实例，修复前后）：

```
修复前：exit 30，无记录
修复后：{"event":"run_complete",...,"cash_proved_optimal":true,"scip_proved_optimal":true,
         "final_lb":"45","final_ub":"45","final_incumbent":"45",...,"exit_reason":"optimum_scip"}
exit=0
```

### 顺带发现的缺陷五：SCIP 重试把时限抬到 615 秒

`ScipSolver.cc:231` 的重试启发式：SCIP 打满时限且 gap<10% 时 `opt_scip_cpu +=
opt_scip_cpu_add`（15+600=615 秒）。在嵌入协议里等于把 15 秒窗口改成 615 秒，让 SCIP 重新
吞掉预算——缺陷一（SCIP 首调用吞预算）换了条路径回来。`frb25-13-1` 上这一点看得最清楚：
修复前 SCIP 靠 615 秒重试磨到最优再 `_Exit(30)`；加了 `!opt_embedded_runner` 守卫后，SCIP
只拿 15 秒、证不出就正常交还 CDCL，该实例变成 `final_lb 299 / final_ub 300` 的预算结束
（最优 300，差 1），而不是消失的记录。

### 影响与结论

三个失败实例是同一「exit 30」缺陷的三条内部路径，全部修复。旧二进制那批 26 次失败全部作废，
`runs/debug50` 已移入 `runs/debug50.invalid-exit30` 归档，用新二进制从头重跑（见 §9）。
Stage 2 因 MSE24W 无读权限（`-rwxr-x---`，属主 caiyujie），按用户决策**只跑 MSE23W**。

## 10. 缺陷六：看门狗与协调器用两套时钟，混合运行被提前打断且记录失真

### 现象

Stage 1 跑到 228 次运行时，18 个四配置齐全的实例里出现一批「Hybrid 明显差于 CASH」的
记录，其中最刺眼的是 `causal-discovery_wt-causal_Link_10_1000`：

```
CASH   : cash_proved_optimal=true  final_lb=final_ub=1917853  exit_reason=optimum  wall=352s
Hybrid : cash_proved_optimal=false final_lb=196969 final_ub=195887747 exit_reason=budget wall=603s
```

同一实例，纯 CASH 352 秒**证明最优**，混合跑满 600 秒上界纹丝不动。同时混合的 stdout 只有
6 行（没有任何 `Found solution`，也没有 `CASHWMaxSAT resources usage` 统计块），而 CASH 有
63 行。

### 定位

混合记录的 `scip_seconds` 是 **0**。这在正常路径上不可能：`apply_scip_limit()` 无条件返回
自己的参数，而两个调用点传的都是 `options.scip_seconds > 0 ? ... : cash_window_seconds`，
即至少 15。0 只可能来自**回退路径**——看门狗。

`start_watchdog(budget)` 起的线程从**进程启动**时刻睡 `budget + 3` 秒
（`hybrid_main.cpp:290-295`），到点后**默认构造**一个 `RunSummary`（`hybrid_main.cpp:302`），
只从 `pb_solver` 填 `final_lb/ub/incumbent`，然后用 `exit_reason = "budget"` 发布记录并
`_Exit(0)`。于是这条记录里：

- `scip_seconds` 是默认值 0（真实值 15）——**因此 `scip_seconds == 0` 是「看门狗写的」的可靠指纹**
- `cash_deadline_polls` 是默认值 0，**不能**读成「终结器没被问过」
- `spb_certificate_ub` 是默认值 `null`
- `exit_reason` 是 `"budget"`，与正常的预算结束**无法区分**
- 最要命的是它**跳过 SPB 证书回填**（只有正常路径 `hybrid_main.cpp:611-613` 才做），
  所以混合的 `final_ub` 只剩 CASH 分量自己的界，**系统性地低估混合配置**

而两个预算钟的起点并不相同：

| 分量 | 钟起点 | 代码 |
|---|---|---|
| `CashOnlyCallback`（CASH 配置） | 构造时，**在解析之前** | `hybrid_main.cpp:520`，早于 `:523` 的 `parse_WCNF_file` |
| `HybridCoordinator`（混合配置） | **解析之后**的第一个调度点 | `hybrid_coordinator.cpp:158-161` |
| 看门狗 | 进程启动 | `hybrid_main.cpp:293` |

宽限只有 3 秒。**解析超过 3 秒的实例上，看门狗必然抢在协调器之前开火。** 直接验证：

```
$ hybridmaxsat --config CASH   --budget 5 --cash-window 15 ... causal_Link
exit=0  process_wall=5.52s   wall_seconds=6  scip_seconds=15  polls=1944     ← 正常结束

$ hybridmaxsat --config Hybrid --budget 5 --cash-window 15 ... causal_Link
exit=0  process_wall=8.07s   wall_seconds=8  scip_seconds=0   polls=0        ← 5+3，看门狗
```

同样的 5 秒预算，CASH 走正常路径（记录完整），混合被看门狗在 8.07 秒处杀掉（记录失真）。
样本里 **54 次混合运行有 17 次（31%）是这类坏记录**，且它专挑解析慢的大实例——正是决定
「混合 vs 纯 CASH」这个比较的那些实例。

### 影响

这条缺陷直接污染 Stage 1 的分析结果，必须先修再进 Stage 2。修法有三处：

1. 看门狗计时起点改成**与求解器同一原点**（解析之后），或把宽限放大到大于最大解析时间；
2. 看门狗记录改用**独立的 `exit_reason`**（如 `budget_watchdog`），不再冒充 `budget`；
3. 看门狗记录补上 SPB 证书回填，否则混合的界被系统性低估。

### 待查：窗口是否本身就在破坏 CASH 的搜索

即使剔除坏记录，仍有 `causal-discovery_wt-causal_alarm_9_1000` 这样的**正常结束**运行显示
混合差 11 倍（1233992 vs 13720163）。90 秒探针显示交接周期精确为 **18.008s = 15 + 3.008**，
即协议被严格遵守、SPB 并没有超时，所以差异不能归给「SPB 抢走 1/6 时间」。同一实例上
CASH-only 的冲突数是 378817，混合只有 2745（差 138 倍）。

控制实验（`causal_Link`，`--budget 300`，只改 `--cash-window`）把两种解释分开了：

| `--cash-window` | SPB 轮次 | `Found solution` 行数 | final_lb | final_ub |
|---|---|---|---|---|
| 300（窗口覆盖整个预算，从不打断） | 0 | **2** | 1800906 | **1917853（=最优）** |
| 60（只打断 4 次） | 4 | **0** | 266972 | 195887747 |
| 15（打断 16 次） | 16 | **0** | 196969 | 195887747 |

结论很硬：**决定性的变量是「有没有打断」，不是「被拿走了多少时间」。** 不打断时 CASH 在
300 秒内找到最优 1917853；只要发生哪怕一次窗口打断（60 秒窗口，4 轮），CASH 在整个 300 秒里
**一个解都找不到**（`Found solution` 为 0），退回到初始平凡上界 195887747。所以差异不来自
「SPB 抢走 1/6 的时间」，而来自**窗口边界打断 CASH 的 SAT 调用后它的搜索无法恢复**。

这一点对本工作是要害：混合协议的前提是「CASH 的 CDCL 主循环可以在窗口之间反复暂停-恢复」，
而实测在 MSE23W 的大实例上，暂停-恢复的代价不是按比例损失时间，而是**搜索归零**。这也解释了
为什么 18 个四配置齐全的实例里有 9 个「完全相同」——那 9 个是 CASH 在**第一个窗口内**就证出
最优、根本没被打断，两个配置跑的是同一段代码。

**结论：把 CASH 的传播推理值作为 SPB 初始解，没有带来可测量的收益。** 混合配置相对纯
CASH 的全部 UB 改善，都来自「SPB 独立跑 3 秒」这件事本身，与推理传递无关。

但窗口本身已经把 CASH 削弱了（§10 控制实验：`causal_Link` 上被窗口打断的 CASH 从头到尾

SPB 强，也可能只是协议把 CASH 打弱了、SPB 在填坑。这两种解释对设计的含义正好相反。

## 12. 「SPB 的时间是不是太少」——窗口扫描实验

§11 的结论引出一个自然的反驳：既然中途改善能让更多软子句硬化
（`MsSolver.cc:315-321`，判据 `weight > UB − LB`），那么 SPB 拿到的 3 秒是不是根本不够
——每次都是"刚开始搜索就结束了，因为还要预处理和其他的输入"？如果成立，就该加大
`--spb-window`，收益会随窗口线性上升。

### 12.1 实验设计

关键是区分两种解释：

| 解释 | 预测 |
|---|---|
| 每轮有固定开销（重建状态/重新输入），3 秒里真正在搜索的没几秒 | hybrid@3s 应**明显差于** standalone SPB@3s |
| 3 秒就是 3 秒搜索，只是时间本身短 | hybrid@3s 应**不差于** standalone SPB@3s |

在 `correlation-clustering_wt-...Protein4_BINARY_N320` 与
`ParametricRBACMaintenance_mse20_wt-role_domino_multiple_0.6_8` 上各跑：
hybrid（`--cash-window 15 --spb-window {3,10,30}`，budget 300）与
standalone SPB（cutoff {3,10,30,300}），seed 20260909。
脚本 `scripts/probe_spb_window.sh`，输出 `runs/probe2/`。

### 12.2 结果

role_domino（越小越好）：

| SPB 时间 | hybrid 各轮最好 spb_ub | hybrid 最终 UB | standalone SPB |
|---|---|---|---|
| 3s | 159968 | 159968 | 162400 |
| 10s | 157162 | **157162** | 158055 |
| 30s | 157162 | 157162 | 157017 |
| 300s | — | — | 156959（运行 302s） |

correlation-clustering：

| SPB 时间 | hybrid 各轮最好 spb_ub | hybrid 最终 UB | standalone SPB |
|---|---|---|---|
| 3s | 12949878 | 12949878 | 14049820 |
| 10s | 12949878 | 12949878 | 13753624 |
| 30s | 12949878 | 12949878 | 13753624 |
| 300s | — | — | 13099956（运行 300s） |

### 12.3 结论：窗口不是瓶颈

**（1）3 秒就是 3 秒搜索，没有被预处理吃掉。**
两个实例上 hybrid@3s 都**优于** standalone SPB@3s
（159968 < 162400；12949878 < 14049820），correlation 上甚至优于 standalone SPB@300s
（12949878 < 13099956）。这说明每轮确实拿到了完整的 3 秒搜索时间——
这有代码层面的解释：实例只在第一轮解析一次（`local_search_solver.cpp:89-114`
的 `persistent_worker_`），后续轮次直接复用，不存在每轮重新输入的固定开销。
用户假设的"还没开始就结束了"在数据上不成立。

**（2）加长时间收益很小且很快饱和。**
role_domino 从 3s 到 30s 只改善 1.76%（159968→157162），从 30s 到 300s 再改善 0.04%
（157017→156959）。correlation 上窗口从 3s 加到 30s **完全没有收益**
（12949878 恒定）。即 SPB 的收益在 10–30 秒量级就饱和了。

**（3）加长时间要拿 CASH 的搜索时间换，而这正是最脆弱的部分。**
`--spb-window 30` 时一个周期 45 秒，300 秒预算下 SPB 拿到 180 秒、CASH 只剩 90 秒。
代价是 §10 实测的：CASH 被**一次**打断就再也回不到最优（causal_Link 窗口化后
`found=0`，不打断则证明最优）。用 1.76% 的解质量去换 CASH 的证明能力是不划算的。

**（4）第一轮是最有价值的一轮。**
correlation 上第 1 轮就返回了全程最好的 12949878，后续轮次返回的都更差。
这与 §11.4 的消融空结果一致：CASH 的初始传播解是最好的热启动，
后续交接的初始解质量在下降。

### 12.4 顺带发现：缺陷六随窗口变长而必然触发

`--spb-window 30` 的两个 hybrid 记录 `scip_seconds` 都是 **0**，即由看门狗写出，
进程在 303 秒被 `_Exit(0)`。原因是结构性的：

`hybrid_coordinator.cpp:132` 把 SPB 的 cutoff 固定为 `spb_window_seconds`，
**从不按剩余预算裁剪**：

```cpp
settings.cutoff_time = schedule.spb_window_seconds;
```

而 `should_stop()`（`:200-205`）只在调度点被咨询。于是最后一轮 SPB 从
t≈295s 起跑、要跑到 t≈325s，超出协调器预算 25 秒，而看门狗的宽限期只有 3 秒
（`hybrid_main.cpp:291`）——看门狗必然先开枪，并写出一条
`scip_seconds=0` / `spb_certificate_ub=null` / 跳过 SPB 证书回填的坏记录。

宽限期（3s）小于一个 SPB 窗口（30s），所以**窗口越长、坏记录越多**：
3s 窗口时超时 ≤3s ≈ 宽限期，通常能活到协调器自己收尾；30s 窗口时几乎必死。
这解释了缺陷六约 31% 的发生率，也给修复补了第三项：
看门狗宽限期必须 ≥ 一个 SPB 窗口，或 SPB 的 cutoff 必须按剩余预算裁剪。

## 14. 实验没有效果的原因分析

主结果（§13.2）：CASH 证明 108/150，Hybrid 81/150，**净亏 27 次，净赚 0 次**。
本节把"为什么"落到证据上，并区分**已证实的原因**与**待验证的假设**。

### 14.1 已证实：27 次损失全部落在 CaDiCaL 的桶里

按 `exit_reason` 拆开，两个配置的证明来源完全不同地受影响：

| 配置 | `optimum`（CaDiCaL） | `optimum_scip`（ILP） | `budget` |
|---|---|---|---|
| CASH | 99 | 9 | 42 |
| Hybrid | **72**（−27） | **9**（±0） | 69（+27） |

成对比较（150 个实例×种子格子）：**CASH 独占 27、Hybrid 独占 0、共同 81、都没证 42**。
27 次的转移**无一例外**是 `optimum → budget`。

这是最关键的一条：如果只是"时间被分走 20%"，两个桶应该同比例下降。
实际上 **ILP 路径毫发无伤，只有 CaDiCaL 的完整搜索被打断清零**。
CDCL 求解器依赖持续的 trail、重启调度和子句数据库学习；每 15 秒被抢占一次，
这些状态反复作废，等于不断从头开始。§10 的控制实验已经单独验证过这一点
（causal_Link：窗口 300 秒 → 证明最优；窗口 60 秒 → `found=0`；窗口 15 秒 → `found=0`，
**一次打断就够**）。

### 14.2 已证实：成本每轮必付，收益依赖稀有事件

轮级统计（§11.1，Hybrid 共 1543 轮）：

| | 轮数 | 占比 |
|---|---|---|
| SPB 返回了可行解 | 914 | 59.2% |
| ├ 优于 CASH 当时的界 | **64** | **7.0%** |
| ├ 相等 | 344 | 37.6% |
| └ **比 CASH 更差** | **506** | **55.4%** |

也就是说，**典型的一轮是：CASH 白白让出 3 秒搜索时间 → SPB 交回一个更差的解 →
CASH 拒绝它**。成本（打断）是无条件支付的，收益（提升 UB）要求一个 7% 概率的事件。
期望值显然为负。

### 14.3 已证实：硬化反馈链在第一个环节就断了

这条直接回应用户提出的假设（"中途改善就能让更多软子句硬化"）。

机制本身是对的，`MsSolver.cc:315-321`：

```cpp
Int UB = (!scip_foundUB ? UB_goalvalue : min(UB_goalvalue, scip_UB));
Int Ibound = UB - LB_goalvalue;
weight_t wbound = (Ibound >= WMAX ? WEIGHT_MAX : toweight(Ibound));
for (int i = top_for_hard - 1; i >= 0 && soft_cls[i].fst > wbound; i--)
```

判据是 `weight > UB − LB`：UB 越低 → 区间越窄 → **越多**子句被硬化。

**但在混合协议下 CASH 的 UB 根本不改善。** §10 的控制实验记录得很清楚：
窗口化的 CASH `found=0`，UB 冻结在初始值 **195887747**；而 Stage 1 中
causal_Link 三个种子的 hybrid 记录值是 **195887747 / 154915005 / 195887747**
—— 与初始值一字不差（两个种子完全相等，第三个也只有一档差异）。

UB 不动 → `UB − LB` 不缩小 → **没有任何子句被额外硬化**。

所以真实的因果链不是"硬化得不够多"，而是：

> 打断摧毁 CASH 的搜索 → CASH 的 UB 冻结在初始值 →
> `UB − LB` 从不缩小 → **硬化从未被触发**

链条断在第一环，不在最后一环。

### 14.4 已证实：混合在两个组件都该赢的地方同时输

在 27 个失败实例上，把 hybrid 的最终 UB 与 CASH-only、standalone SPB 对比：

| 结果 | 数量 |
|---|---|
| hybrid 比**两者都差** | **12 / 27** |
| hybrid 比 CASH-only 差 | 18 / 27 |

最极端的是 causal_Link（三个种子一致）：

| 配置 | 最终 UB | exit_reason |
|---|---|---|
| CASH-only | **1,917,853** | optimum（证明最优） |
| SPB-alone | 33,562,494 | budget |
| Hybrid | 195,887,747 | budget |

hybrid 比最优值差 **102 倍**，比**单独的 SPB** 还差 **5.8 倍**。

这条的意义：协议不是"用 CASH 的搜索能力换 SPB 的解质量"，而是**同时破坏了两者**。
hybrid 的 UB 连 SPB 单独跑都达不到，说明 SPB 在协议里也没能发挥它自己的水平。

### 14.5 已证实：SPB 每轮从零开始，进度不累积

`local_search_solver.cpp:38-48` 的 `begin_search()` 每轮重建解池；
`lsworker_search.cpp:136-199` 每次 try 都重新 `init()` 并重置
`total_step`、`opt_unsat_weight`、`best_soln_feasible`。跨轮持久化的**只有权重**。

所以协议实际执行的是"**跑了 33 次 3 秒**"，而不是"连续跑 100 秒"。
§12 还发现一个反直觉现象：correlation-clustering 上**第 1 轮就给出了 SPB 全程最好的值**
（12949878），后续轮次返回的都更差——因为 CASH 的初始传播解是最好的热启动，
越往后交接的初始解质量越低。

### 14.6 待验证的假设（需要额外实验，不能当结论）

| # | 假设 | 检验方式 |
|---|---|---|
| H1 | 窗口参数（15/3）从未被调优，可能存在能赢的设置 | 全量扫描 cash-window ∈ {15, 60, 150}；但 §10 提示 60 秒仍会输 |
| H2 | 600 秒预算选错了 regime，混合的优势在更短或更长的预算下才显现 | 同一批实例跑 budget ∈ {60, 300, 3600} |
| H3 | 主指标（证明数）恰好是协议最伤的属性，换成解质量 gap 结论会不同 | 用 §11 的 UB 数据重算 gap 指标 |
| H4 | 交给 SPB 的初始解（CASH 赋值投影到原始变量）质量不足 | 对比投影赋值 vs 随机赋值 vs SPB 自己的池 |
| H5 | `settings.solution_pool_size = 1` 的假设有误，SPB 丢了最优解记忆 | 改成 20 重跑，看轮级最好值是否改善 |
| H6 | CASH 的 UB 冻结是 CaDiCaL 重启调度被打断，还是交接本身的开销 | 在 CASH 内部埋点，分离"被打断"与"交接耗时" |

### 14.7 如果要在负面结果之外找出路

三条方向，按可行性排序：

1. **不打断 CASH。** SPB 只在 CASH **自然收敛点**介入（例如 CASH 连续 N 秒
   没有改进 UB 才让出时间片），或 CASH 跑满预算后 SPB 只做最终修复。
   §14.1 说明损害来自"打断"，不是来自"给了 SPB 时间"——两者的区别是全部关键。

2. **把 SPB 从"控制流参与者"降级为"UB 来源"。** 在 CASH 内部作为一次
   启发式调用（类似 SCIP 的角色），而不是一个抢占时间片的独立阶段。
   注意 ILP 路径（`optimum_scip`）9 = 9 未受影响，说明
   "外部求解器只提供界、不打断搜索"这个模式在该架构里是**可行**的。

3. **换指标。** §11 的数据显示混合在解质量上确有 6 个实例的胜利。
   如果毕设的假设可以改成"混合改善了难实例的解质量"，那是一个**正面**结论；
   但它不能同时声称"提高证明能力"。

## 15. 全量实验（2 配置 / 单种子 / 558 实例）

`batch=full2cfg`，`--configs CASH,Hybrid --seeds 20260909 --workers 96`，
budget 600 / cash-window 15 / spb-window 3。**1116 次运行，0 个 problems。**
（运行期间 S122 网络中断约 1 小时，机器未重启，批次自行跑完。）

### 15.1 主结果

| 配置 | 证明最优 | 比例 |
|---|---|---|
| CASH | **398/558** | **71.3%** |
| Hybrid | 286/558 | 51.3% |

成对（558 个实例）：

| | 数量 |
|---|---|
| 仅 CASH 证明 | **112** |
| 仅 Hybrid 证明 | **0** |
| 两者都证明 | 286 |

### 15.2 决定性发现：只要发生过一次交接，证明就没了

这是本次实验最强的结果。按"混合运行是否真的发生过交接"（`rounds > 0`）拆开：

| 组 | 运行数 | Hybrid 证明 | 比例 | 同批实例上 CASH 证明 |
|---|---|---|---|---|
| **0 轮**（未交接） | 293 | 286 | 97.6% | 293/293（100%） |
| **≥1 轮**（已交接） | 265 | **0** | **0.0%** | 105/265（39.6%） |

**265 个发生了交接的运行，没有一个证明出最优**——而同样这 265 个实例，
纯 CASH 证明了 105 个。

这不是"交接让证明变慢"，而是"**交接让证明不再发生**"。
它把 §10 控制实验的结论（一次打断就够）从单个实例推广到了全量：
265 次独立试验，0 次例外。

### 15.3 这个 0 不是记录假象（已核验）

265 个交接运行里有 **100 条是缺陷六的看门狗记录**，而看门狗记录由默认构造的
`RunSummary` 写出，`cash_proved_optimal` **恒为 false**。所以必须排除"证明被记录器掩盖"。

两道检验（`scripts/mask_check.py`、`scripts/close_check.py`）：

1. **界的闭合情况**：100 条中 `lb == ub` 的有 **0** 条。（57 条两个界的位数相差 ≤1，
   即相差不到 10 倍，属于"接近"但不构成证明。）
2. **UB 是否已是最优**：一个即将证明最优的运行，其 UB 必须**已经等于最优值**
   ——证明是关闭最后一段间隙，不是发现新解。按此检验这 100 条：
   * **82 条**的 UB **严格差于** CASH-only —— 这些运行时**不可能**正在进行证明；
   * **17 条**恰好持有 CASH-only 的 UB（其中 8 条 CASH 曾证明该实例，9 条没有）；
   * 1 条无对应 CASH 运行可比。

**结论**：最多只有 17 条存在"被最后几秒切断"的理论可能，其中真正的疑点只有
**8 条**（持有最优 UB 且 CASH 证明过）。即使这 8 条全部被掩盖，结论也只是
从 **112 : 0** 变成 **112 : 8**，不影响任何判断。

| 更好 | 100 |
| 相等 | 353 |
| 更差 | 105 |

与 §11.5 一致：混合在**解质量**上大致打平（100 胜 105 负），
在**证明能力**上净负 112。两个指标给出相反方向的结论，
而毕设的主指标是后者。

## 16. 缺陷七：一个任务的异常被静默吞掉，批次仍报"成功"

### 现象

`full2cfg` 报告 **1115/1116，0 个 problems**。但 `abstraction-refinement_wt-polysite-bloat`
的 CASH 运行只有 `stdout.log`，**没有 `status.json`**，也没有 FAIL 行——
既不算运行成功，也不算失败。

### 定位

该实例的界有 **421,807 位十进制数字**（权值极大），而 `validate()` 里的
`int(low) > int(high)` 触发 CPython 的整数转换上限（默认 4300 位）：

```
ValueError: Exceeds the limit (4300) for integer string conversion:
value has 421807 digits; use sys.set_int_max_str_digits() to increase the limit
```

`ThreadPoolExecutor` 的 future 异常被 `except` 捕获并 `log` 了，但：

* `stopper.stop()` 只停止**提交**新任务，而 1116 个任务早已全部提交，
  所以"提前停止"什么也没停住，只是打了一句误导性的 `BATCH STOPPED EARLY`；
* 退出码是 `1 if failed else 0`，而 `failed` 只统计 `statuses` 里有 `problems` 的，
  崩溃的任务根本不在 `statuses` 里——**批次以 0 退出，报告"成功"**。

即：**一个任务凭空消失，批次仍然报成功。**

### 修复（三处）

1. `compare_bounds(a, b)`：不转 `int`，按"先比位数、再字典序"比较十进制字符串。
   对非负十进制整数结果与数值比较完全一致，且是线性的。
2. `brief(value)`：日志里截断长界（40 位 + 总位数），不再往日志里灌 400KB 数字。
3. 收集 future 时把异常任务记进 `crashed` 列表，计入退出码与最终统计行；
   `BATCH STOPPED EARLY` 改为措辞准确的 `stopper fired`。

### 验证

用修复后的脚本单独补跑该实例（`batch=backfill_bloat`）：**1 run, ok=1, failed=0**，
`status.json` 正常写出。全套 1116 次运行现已全部有记录。
